# **1. 目的**

個人のパーソナルトレーナーが

セッション提供後に未収金を意識せず、指導に集中できる状態を作るため、

請求確定および請求通知を自動で行う。

本設計は 「請求確定＋初回請求通知」 のみを対象とする。

# **2. 対象ユースケース**

トレーナー側の業務フロー（セッション完了等）を起点として、

請求が自動的に確定され、顧客に請求通知が送信される

# **3. スコープ**

**3.1 本設計に含めるもの**

- 請求確定要求の受付
- 請求データの生成・確定
- 請求データの永続化
- 請求通知（メール）の送信

**3.2 本設計に含めないもの**

- 金額計算ロジック
- セッション管理・指導中機能
- 支払い処理（決済）
- 未収判定・督促・再通知
- 請求内容の編集・修正

# **4. 前提条件（不変）**

- 請求は「金と責任の記録」であり、業務状態は管理しない
- 請求確定後、金額・期限・対象は変更しない
- 請求確定と通知送信は分離する
- 通知失敗時でも請求は確定済みとする
- 請求対象は汎用IDで扱い、業務種別は解釈しない

# **5. 責務定義（レイヤ別）**

## **5.1 Billing ドメインモデルの責務**

Billing ドメインモデルは、請求の「確定」に関する中核的な責務を持つ。

### **責務範囲**

1. **金額の正規化**
   - 受け取った金額（小数を含む）を整数に切り捨てる
   - あらゆる金額決定ロジックに切り捨て処理を実装させないため

2. **最低限のガード**
   - 切り捨て後に1円未満（0以下）になる金額は受け入れない
   - 防衛的プログラミングとして実装

3. **支払期限の紐付け**
   - 受け取った支払期限を請求に紐付ける
   - 最低限の日付チェック（未来日付であること）を実施

4. **状態遷移の管理**
   - 未確定（DRAFT）状態から確定（CONFIRMED）状態への遷移のみを許可
   - 必ず未確定の状態を受け取り、確定状態にする

5. **不変性の保証**
   - 確定後、金額・期限・対象ユーザーIDは変更しない

### **責務外（他のレイヤの責任）**

1. **金額の決定ロジック**
   - セッション料金計算
   - 割引計算
   - 税計算
   - → これらは起点側業務フローの責任

2. **支払期限の決定ロジック**
   - 何日後に設定するか
   - 営業日計算
   - 最低期間の設定
   - → これらは起点側業務フローの責任

3. **詳細な妥当性チェック**
   - 金額の上限・下限チェック
   - 詳細な日付検証
   - → これらは起点側業務フローの責任

### **設計原則**

- **「受け取った値を必ず確定する」**
  - 金額決定は責任外なので、受け取った金額を信頼する
  - ただし、最低限のガード（1円未満拒否）は実装する

- **「最低限のチェックのみ実施」**
  - 支払期限が未来であることのみチェック
  - 詳細なビジネスルールは起点側の責任

## **5.2 請求確定を指示する責務（Application Layer）**

- 起点側業務フローから請求確定要求を受け取る
- 入力データの最低限の妥当性を確認する
- 請求生成・確定処理を呼び出す

## **5.3 請求通知を送る責務**

- 確定済み請求情報をもとに通知を送信する
- 通知結果は請求状態に影響させない

# **6. 入力データ仕様（請求確定要求）**

起点側業務フローから、以下の情報が渡される。

| **項目** | **説明** |
| --- | --- |
| customerId | 請求対象の顧客ID |
| billingTargetId | 請求対象を示す汎用ID |
| billingTargetType | 対象種別（例：SESSION / RESERVATION） |
| billingAmount | 請求金額（小数含む、ドメインで切り捨て） |
| paymentDueDate | 支払期限（未来日付） |

**重要な設計判断**：

- **金額計算は起点側の責任**
  - 請求側では再計算・精査を行わない
  - 小数を含む金額もそのまま受け取る
  - Billing ドメインが切り捨てを実施

- **支払期限決定は起点側の責任**
  - 請求側では期限の再計算を行わない
  - Billing ドメインが未来日付かのみチェック

# **7. 請求データ仕様（確定時に固定）**

請求確定時、以下の情報を固定する。

| **項目** | **説明** |
| --- | --- |
| billingId | 請求ID |
| customerId | 請求対象顧客 |
| billingTargetId | 請求対象ID |
| billingTargetType | 対象種別 |
| billingAmount | 請求金額（整数、切り捨て後） |
| paymentDueDate | 支払期限 |
| billingStatus | CONFIRMED（確定済み） |
| billingConfirmedAt | 請求確定日時 |

# **8. 処理フロー**

**8.1 全体フロー**

起点側業務フロー

↓ 請求確定要求

請求確定受付

↓

請求生成・確定（Billing ドメイン）

↓

請求Repository（INSERT）

↓

請求通知送信

**8.2 詳細フロー**

1. 起点側から請求確定要求を受信する
2. 必須項目（顧客ID・金額・期限）の存在を確認する
3. 請求IDを採番する
4. **Billing ドメインで請求を生成**
   - 金額を切り捨てて整数化
   - 1円未満は拒否
   - 支払期限が未来かチェック
5. **Billing ドメインで請求を確定**
   - DRAFT → CONFIRMED へ状態遷移
   - 確定日時を記録
6. 請求データをDBに保存する
7. 保存済み請求情報をもとに請求通知を送信する

# **9. エラーハンドリング方針**

- **請求生成失敗時**（金額が1円未満など）
  → 処理を中断し、請求は確定しない
  
- **請求確定失敗時**（期限が過去など）
  → 処理を中断し、請求は確定しない

- **請求保存失敗時**
  → 処理を中断し、請求は確定しない

- **通知送信失敗時**
  → 請求は確定済みとし、エラーのみ記録する

# **10. 将来拡張を想定した設計ポイント**

- 請求対象は汎用ID＋種別で保持しているため、
    - セッション
    - 予約
    - その他業務
    に拡張可能

- 金額算出ロジックは請求責務に含まれていないため、
    - Strategy
    - Factory
    による後付けが可能

- 支払期限決定ロジックも同様に拡張可能

# **11. 設計方針まとめ**

- **請求は業務を知らない**
  - セッション・予約などの業務種別は解釈しない
  - 汎用IDで扱う

- **請求は金額を決めない**
  - 金額計算は起点側の責任
  - 受け取った金額を切り捨てて整数化するのみ

- **請求は期限を決めない**
  - 支払期限決定は起点側の責任
  - 未来日付かの最低限チェックのみ

- **請求は「確定」を責務とする**
  - 未確定 → 確定への状態遷移を管理
  - 確定後の不変性を保証

- **境界は契約（入力データ）で守る**
  - 入力データの妥当性は起点側が保証
  - ドメインは最低限のガードのみ実施

# **12. テスト戦略**

Billing ドメインモデルのテストでは、以下の責務範囲を網羅する。

**テスト対象**：
- ✅ 金額の正規化（小数 → 整数への切り捨て）
- ✅ 1円未満の金額の拒否
- ✅ 支払期限の未来日付チェック
- ✅ 状態遷移（DRAFT → CONFIRMED）
- ✅ 確定後の不変性保証

**テスト対象外**：
- ❌ 金額計算ロジック（起点側の責任）
- ❌ 支払期限決定ロジック（起点側の責任）
- ❌ 詳細な妥当性チェック（起点側の責任）
