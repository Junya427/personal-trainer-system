# 顧客情報登録フロー 全体設計

# **1. このフローの目的**

- 顧客情報と支払い方法を 同時に登録 する
- 自動引き落とし可能な顧客だけをDBに作る
- 決済代行SDKを使って トークンを取得・保存 する
- この時点では 請求は一切発生しない

# **2. やらないこと（明確な非スコープ）**

- 仮顧客・途中保存
- 顧客だけ／支払い方法だけの登録
- トークン単体の保存
- 登録失敗時の自動リカバリ
- UIの作り込み（最小UIのみ）

# **3. エンティティ設計**

**Customer（顧客）**

| **項目** | **説明** |
| --- | --- |
| id | 顧客ID |
| name | 氏名 |
| address | 住所 |
| phoneNumber | 電話番号 |
| paymentMethodId | 支払い方法ID |
| consentFlag | 自動引き落とし同意（trueのみ） |
| metadata | 任意 |

不変条件

- 支払い方法が紐づいていない顧客は存在しない
- 同意していない顧客は存在しない

**PaymentMethod（支払い方法）**

| **項目** | **説明** |
| --- | --- |
| id | 支払い方法ID |
| type | 種別（クレカ / 口座） |
| token | 決済代行が発行したトークン |
| isActive | 有効フラグ |
| registeredAt | 登録日時 |
| disabledAt | 無効化日時 |
| metadata | 任意 |

責務

- 有効／無効の管理は支払い方法エンティティの責任

# **4. 顧客登録成立条件（最重要）**

Customer と PaymentMethod が同時に存在する時だけ、登録は成立する

- どちらか一方だけは作らない
- 登録失敗は「存在しなかったこと」にする

# **5. 顧客登録フローID（顧客登録フローID）**

**定義**

- customer_registration_flow_id
- 顧客IDでも決済IDでもない
- 登録途中のフローを識別するための一時ID

**目的**

- 顧客入力画面とSDK画面を同一登録作業として結びつける

# **6. フローIDの保持方法**

**採用方式**

- HTTP Only Cookie

```
Set-Cookie: customer_registration_flow_id=xxx;
HttpOnly;
Secure;
SameSite=Lax
```

**理由**

- URL改竄不可
- JSから触れない
- SDK画面遷移後も保持される
- 戻り時に自動送信される

# **7. フローIDの寿命と失効条件**

**寿命（TTL）**

- 30分
- 延長なし
- 再利用不可

**失効（執行）条件**

| **条件** | **処理** |
| --- | --- |
| 登録成功 | 即失効（使用済み） |
| 登録失敗 | 何もしない（TTLで自然失効） |
| SDK離脱 | 何もしない（TTLで自然失効） |
| TTL切れ後のwebhook | 無視 |

# **8. フロー全体の時系列**

1. 顧客情報入力開始
2. サーバが 顧客登録フローID を発行
3. Cookieに保存（TTL 30分）
4. 決済セッション作成APIを呼ぶ
5. SDK画面にリダイレクト
6. ユーザーが支払い情報入力
7. 決済代行が結果確定
8. webhook（成功 or 失敗）がサーバに届く
9. successUrl / cancelUrl に戻る

# **9. webhook の扱い**

**成功 webhook**

**条件**

- フローIDが有効
- 顧客情報が存在
- トークンが存在

**処理**

- Customer + PaymentMethod を 同一トランザクションで insert
- フローIDを即失効
- 登録完了状態にする

**失敗 webhook**

**処理**

- 何もしない
- DB変更なし
- フローIDはTTLまで残る

# **10. トークンだけ来た場合の扱い**

- 顧客情報とトークンが 両方揃わなければ登録しない
- トークン単体は保存しない
- 次回は 顧客情報入力からやり直し

# **11. 画面遷移ルール（成功／失敗）**

**共通原則**

- UIは原因を断定しない
- 真実は DBの状態

**11-1. 成功時の画面遷移**

**条件**

- webhook（成功）受信済み
- 顧客登録が成立している

**振る舞い**

- SDK → successUrl
- サーバが状態確認
- 登録完了画面に遷移

**成功画面の内容**

- 「登録が完了しました」
- 次の行動のみ提示
- 請求・金銭の話は出さない

**11-2. 失敗時の画面遷移**

**条件（いずれか）**

- webhook failure
- webhook未到達
- トークンのみ存在
- フローID無効／期限切れ

**振る舞い**

- SDK → successUrl / cancelUrl
- サーバが状態確認
- エラーメッセージ付きで顧客情報入力画面へ

**表示メッセージ例**

- 「登録が完了していません」
- 「もう一度情報を入力してください」

※ 失敗理由の詳細は表示しない

※ SDK側UIに任せる

# **12. UIの責務**

- SDK側UI
    - 入力エラー・詳細理由の表示

- 自前UI
    - 成立／未成立の状態表示
    - 再入力導線を出すだけ

# **13. 今回の実装KPI**

最小UIからSDKを呼び出し、

トークンを取得し、

顧客＋支払い方法を正しく保存できること

- React不要
- 静的HTML＋リダイレクトで十分

# **最終まとめ（設計の芯）**

登録は

「顧客情報 × 決済成功」

が同時に揃った瞬間にだけ成立する

この設計で、

未収金・中途半端な顧客・後処理地獄は発生しない。

このまま実装していい。
