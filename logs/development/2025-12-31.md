## 学んだこと

### TypeScriptのエラーメッセージの読み方
- **`() => string` の意味**: 引数なし、string を返す関数の型
- **アロー構文の読み方**:
  - `() => string`: 引数なし、stringを返す
  - `(x: number) => string`: number を受け取り、string を返す
  - `(x: number, y: string) => void`: 2つの引数、戻り値なし
- **右矢印（=>）の判断**: 右矢印が含まれる型はすべて関数型（関数・メソッド）
- **よくあるエラー**: 「型 '() => string' を型 'string' に割り当てられない」→ メソッド呼び出し忘れ（括弧なし）

### getter/setterの使い分け（DDDの観点）
- **getter の役割**:
  - カプセル化: private プロパティへのアクセス経路を制御
  - 将来の変更に強い: 内部実装を変更しても外部に影響しない
  - ドメインモデルではすべての private プロパティに追加
- **setter を使わない理由**:
  - ビジネスルールを持つメソッドで変更する（`confirm()` など）
  - setter を使うとビジネスルールが散らばる
  - 値の変更をビジネスメソッド内に閉じ込めることで、ドメインロジックを集約
- **DTOには不要**:
  - DTOはデータ転送のみが役割（ロジックを持たない）
  - public プロパティで十分
  - バリデーションは `@IsNumber()` などのデコレーターで実施

### NestJSの `@Body()` デコレーター
- **役割**: HTTPリクエストのボディを自動的にDTOに変換
- **処理フロー**:
  1. HTTPリクエスト受信（JSON）
  2. `@Body()` デコレーターが作動
  3. DTOのインスタンスを生成
  4. class-validatorでバリデーション
  5. バリデーションOKならメソッドに渡す
- **メリット**: 手動でJSON解析・バリデーションを書く必要がない

### テスト駆動開発（TDD）の判断基準
- **TDD（テスト先行）**: テスト → 実装 → リファクタリング
- **実装後テスト**: 実装 → 動作確認 → テスト
- **機能完成後テスト**: 機能完成 → E2E確認 → テスト追加
- **今回の判断**: 最小限のテスト（Billing.confirm()）を先に書き、その後機能完成を優先
  - 学習プロジェクトでは動くものを作って理解することを優先
  - ただし重要なビジネスロジックはテストで保護

### Prisma 7 の変更点

- **理由**: Prisma 7 で内部構造が変更され、型定義のエクスポート方法が変わった

## 技術的な深掘り

### カプセル化の本質
- **アクセス経路の制御**: private プロパティへの直接アクセスを防ぎ、getter/setter（またはビジネスメソッド）経由でのみアクセス可能にする
- **変更の影響範囲を限定**: getter 内部の実装を変更しても、呼び出し側のコードは変更不要
- **ビジネスルールの集約**: setter の代わりにビジネスメソッド（`confirm()`）を使うことで、ルールがドメインモデルに集約される

### DDDにおける不変性（Immutability）
- **readonly の活用**: `private readonly amount: number` で値の変更を防ぐ
- **状態変更はビジネスメソッドで**: `status` や `confirmedAt` のような変更可能なプロパティも、setter ではなくビジネスメソッド内でのみ変更
- **メリット**: ビジネスルールが散らばらず、ドメインモデルが「真実の単一の情報源」になる

### TypeScript型システムの理解
- **関数型**: `() => ReturnType` で表現
- **メソッドと関数の型は同じ**: TypeScriptでは区別しない
- **型エラーの読み方**: 「型 A を型 B に割り当てられない」→ A（実際の型）と B（期待される型）を比較
