# 開発作業ログ

このディレクトリには、日々の開発作業の記録を時系列で保存します。

## 目的

- デバイス間での作業引継ぎ
- 実装判断の理由を記録
- 学習内容の振り返り
- 過去の意思決定の追跡

## ファイル命名規則

```
YYYY-MM-DD.md
```

例: `2025-12-30.md`

## ログフォーマット

各作業ログは以下のフォーマットに従ってください：

```markdown
# 作業ログ: YYYY-MM-DD

## 実装内容

### 1. [機能名・ファイル名]
- **ファイル**: `path/to/file.ts`
- **実装内容**: 何を実装したか
- **実装意図**:
  - なぜその実装にしたのか
  - どのような技術的判断をしたのか
  - 設計書のどの方針に従ったか

### 2. [次の実装項目]
...

## 学んだこと

- 技術的な学び
- DDDやデザインパターンの理解
- NestJS/TypeScriptの新しい知識

## 次回タスク

- [ ] タスク1
- [ ] タスク2
- [ ] タスク3

## 参考資料

- [参考にしたドキュメント](URL)
- [関連する設計書](../../docs/xxx/design.md)

## 疑問・課題

- 解決できなかった問題
- 次回調査が必要な事項
- 技術的な懸念点
```

## 記入のポイント

### ✅ 良い記録例

**実装意図が明確**:
```markdown
- **実装意図**:
  - Decimal型を採用した理由: 金額計算で浮動小数点の誤差を避けるため
  - billingTargetIdを汎用IDとした理由: 設計書の「請求は業務を知らない」原則に従う
  - NotificationModuleをimportsに追加: 単一方向の依存関係を維持するため
```

**学びを具体的に**:
```markdown
## 学んだこと

- NestJSの`@Module()`デコレーターにおける`imports`、`providers`、`exports`の役割
- DDDの境界づけられたコンテキスト（Bounded Context）の実践
- Prisma Schemaでの`@map()`の使い方（スネークケースとキャメルケースの変換）
```

### ❌ 避けるべき記録例

**実装内容の羅列のみ**:
```markdown
- ファイルを作成した
- コードを書いた
```
→ 理由や意図が不明

**コードのコピペ**:
```markdown
以下のコードを実装しました：
[大量のコード]
```
→ Gitで確認できるため不要。意図を記録する

## 作業終了時のルーティン

```bash
# 1. その日の作業ログは Claude Code が自動生成
# （logs/development/YYYY-MM-DD.md）

# 2. Git管理に追加
git add logs/development/

# 3. 実装ファイルと一緒にコミット
git add .
git commit -m "実装内容の簡潔な説明"

# 4. プッシュ（デバイス間で同期）
git push origin main
```

## 作業ログと設計書の使い分け

| 項目 | 作業ログ（logs/development/） | 設計書（docs/） |
|------|------------------------------|----------------|
| 内容 | When（いつ）+ How（どのように） | What（何を）+ Why（なぜ） |
| 時間性 | 時系列に依存 | 時間に依存しない |
| 更新 | 追記のみ（過去は変更しない） | 設計変更時に更新 |
| 記述者 | Claude Code（自動） | 開発者（手動） |
| 例 | "2025-12-30にPrismaServiceを実装。その理由は..." | "請求は業務を知らない（設計方針）" |

## 作業ログとコミットメッセージの使い分け

| 項目 | コミットメッセージ | 作業ログ |
|------|------------------|---------|
| 内容 | What（何を変更） | Why（なぜ）+ 詳細 |
| 文量 | 1-2行 | 詳細な記述 |
| 目的 | 変更履歴の追跡 | 判断理由の記録 |
| 例 | "Prismaスキーマ実装" | "PostgreSQLを採用した理由は本番環境での..." |
